# خطة عمل KONFRM التنفيذية — من الوضع الحالي إلى Prototype متكامل

سأعتبر هذه المحادثة من الآن **مرجع خطة التنفيذ**: لا ننتقل لمرحلة جديدة لمجرد أن الكود اتكتب أو الـBuild نجح؛ ننتقل فقط عندما تنتهي المرحلة وظيفيًا ويتم اختبارها فعليًا.

بنيت الخطة على الـMaster Project Context الحالي وعلى قواعد تصميم الـMobile الموجودة في المشروع، خصوصًا أن هدفنا الحالي **Functional Prototype حقيقي لا Production نهائي**، وأن التطبيقات الثلاثة يجب أن تعتمد على Backend/Database مشتركة لا حالات وهمية منفصلة. fileciteturn0file0L1-L20 كما سأعامل الاتساق في المكونات، الـNavigation، الـTypography، الألوان، الأيقونات، الـSpacing والـFeedback كجزء من جودة المنتج نفسها، وليس تجميلًا أخيرًا. fileciteturn0file1L183-L196

---

# أولًا: ترتيب الأولويات

لن نمشي App-by-App؛ أي لا ننهي تطبيق المستأجر بالكامل ثم ننتقل للمالك. هذا خطأ لأنه قد ينتج ثلاثة تطبيقات جميلة لكن غير مترابطة.

الترتيب سيكون:

**قاعدة البيانات → Backend contracts → Cross-App Core Flows → Design System → UI/UX → الحالات الاستثنائية → Security الأساسية → Integration → Live QA → Demo Readiness.**

وسنستخدم **Clusters كبيرة نسبيًا ومترابطة** حتى نقلل استهلاك Antigravity. كل Cluster قد يحتوي عدة Tasks صغيرة، لكن غالبًا أعطيه Prompt واحدًا متماسكًا لينفذها دفعة واحدة، ثم نراجع النتيجة بدل 10 Prompts لنفس المنطقة.

# PHASE 0 — تثبيت نقطة البداية

### Task 0.1 — Baseline Audit

قبل إضافة أي Feature جديدة، Antigravity يعمل فحصًا واحدًا شاملًا:

- التطبيقات الأربعة البرمجية الحالية:
  - `customer-app`
  - `owner-app`
  - `admin-app`
  - `backend`
- Supabase schema الحالي.
- APIs الحالية.
- Authentication الحالي بعد قرار إزالة OTP من الـPrototype.
- Cloudflare Pages.
- Cloudflare Worker.
- GitHub Actions.
- Environment variables.
- Storage.
- البيانات الحقيقية الموجودة.
- الـMocks والـhardcoded data المتبقية.
- أخطاء Console/API الحالية.
- حالة كل Flow حالي.

**الناتج:** خريطة دقيقة لما يعمل وما لا يعمل وما هو Mock وما هو Real.

### Task 0.2 — إزالة OTP كعائق Prototype

طبقًا لقرارنا الأخير:

**لا نضيّع وقتًا حاليًا في OTP.**

نريد Authentication بسيطًا ومستقرًا يسمح لنا بإنشاء حسابات وتجربة التطبيقات مرارًا بدون SMS limits أو OTP rate limits.

لكن Antigravity **لا يحذف معمارية Auth عشوائيًا** بحيث يكسر إمكانية إعادتها لاحقًا؛ المطلوب Prototype authentication مناسب للاختبار.

### Task 0.3 — تنظيف blockers فقط

نعالج:

- Broken API endpoints.
- Auth loops.
- CORS.
- Environment mismatch.
- Wrong production API URLs.
- runtime crashes.
- أخطاء تمنع التجربة.

ولا نقوم الآن بـ:

- mass refactor.
- dependency upgrades لمجرد أنها أحدث.
- إعادة تسمية SOLA → KONFRM في كل repository.
- تحسين architecture غير مؤثر على الـPrototype.

**Gate 0:** أستطيع فتح التطبيقات الثلاثة والدخول والخروج والتجربة بدون blocker تقني أساسي.

# PHASE 9 — Notification Engine

هنا نحقق فكرة:

> **"كله بيسمع على كله."**

لكن ليس معنى ذلك إرسال Notification على كل click.

نحدد **Business Events المهمة فقط**.

| Event | Renter | Owner | Admin |
|---|---|---|---|
| Property submitted | — | ✓ | ✓ |
| Property approved | — | ✓ | Audit |
| Property rejected | — | ✓ | Audit |
| Booking requested | ✓ confirmation | ✓ | visibility |
| Owner approved | ✓ | ✓ | visibility |
| Owner rejected | ✓ | ✓ | visibility |
| Payment success | ✓ | ✓ | visibility |
| Cancellation | ✓ | ✓ | حسب الحالة |
| Dispute opened | ✓ | ✓ | ✓ |
| Payout request | — | ✓ | ✓ |

ثم:

- unread count.
- read/unread.
- timestamps.
- deep linking إلى العنصر المعني.

Push Notifications الحقيقية يمكن تأجيلها إذا كانت ستستهلك وقتًا دون قيمة للـPrototype؛ **In-app notifications أولًا**.

# ما سنفعله يدويًا بدل إهدار كوتا Antigravity

هناك أشياء **لا أريد Antigravity يضيع وقته فيها**.

أنت تستطيع تنفيذ الأمور البشرية البسيطة عندما أطلبها، مثل:

- إنشاء Test account.
- إدخال OTP لو أعدناه لاحقًا.
- أخذ Screenshot.
- تجربة Flow.
- إعطائي شعورك عن الشاشة.
- فتح Supabase/Cloudflare لإعداد بسيط عند الضرورة.
- إضافة Secret إذا احتجنا.
- توفير صور عقارات حقيقية.
- اختبار التطبيق كمالك/مستأجر.
- اتخاذ Business decision.

أما Antigravity:

**Code + DB + API + debugging + tests + Git + deploy + technical verification.**

# ولكن أين نبدأ الآن تحديدًا؟

هنا نقطة مهمة جدًا:

**لن نبدأ من Task 0 وكأن المشروع جديد.**

لدينا شغل موجود بالفعل. والـMaster Context يقول إن Owner → Admin → Published تم إثباته تاريخيًا، بينما آخر blocker مسجل كان Renter Availability وعدم إثبات الـWorker Live. fileciteturn0file0L1044-L1089

لذلك **أول مهمة فعلية من هذه الخطة** ستكون:

### `MILESTONE 01 — Current Reality & Prototype Access Stabilization`

Antigravity يفحص **الوضع الحالي فقط** بعد آخر تعديلاتنا، ثم:

**يثبت Auth التجريبي بدون OTP → يتأكد من الـDatabase/API → يتأكد من Availability → يثبت Owner/Admin/Renter connectivity → ولا يبني Feature جديدة.**

بعد نجاحها نضع أمامها:

**✅ CLOSED — LIVE VERIFIED**

ثم ننتقل مباشرة للـDatabase/Integration Audit، وليس لأي Feature جانبية.

## القاعدة التي سألتزم بها معك في هذه المحادثة

من الآن كلما تنتهي مهمة وتبعث لي تقرير Antigravity:

**أنا أحدد هل المهمة فعلًا انتهت → أحدّث موقعنا في الخطة → أعطيك الـTask التالي فقط.**

لن أقفز بنا إلى أفكار جديدة، ولن أجعل تحسين صغير يفتح إعادة بناء كاملة، ولن أسمح لـAntigravity أن يخترع Business Rules لأن شيئًا أسهل برمجيًا.

**المسار الحاكم:**

**Real Data → Integration → Core Flows → Unified UI → UX → Money → Edge Cases → Polish → Handoff.**
